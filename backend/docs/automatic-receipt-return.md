# Automatic receipt return

The signed Android APK packages the Neon endpoint, receipt root, independent snapshot signer, policy digest, initial domain epoch and state. These are public values; responder bearer tokens and signer private keys are never packaged. Every compatible installation activates the native return adapter without ADB or a per-device build fingerprint allowlist.

An installation with internet and an upload-confirmed original SOS envelope requests its note-free return feed. POST requests bind the exact accepted envelope, verifier public key, verifier ID, boot session, nonce, route, body and cursor to an installation-key signature. A report UUID alone grants no access. The server authenticates before refreshing external time and rechecks custody before disclosure. This uses the already selected ORIGIN_AND_CUSTODY_RELAYS audience. It does not grant incident listing, private note access, responder actions or admin privileges.

Dashboard status changes retain the ordinary private responder audit and create a separate note-free signed status action. A pending signer or snapshot is explicitly reported as pending; it does not turn a saved dashboard status into an offline guarantee. The original signed receipt is never edited or re-signed by relay phones.

The v2 APK deployment policy uses Android SystemClock.elapsedRealtime, including deep sleep, bound to the current boot. The prototype's explicit deployment tolerance is 1000 ppm (0.1 percent), with uncertainty widened accordingly, a maximum 24-hour signed time checkpoint and signed renewal while connected. This tolerance is an engineering deployment assumption, not measured certification of every device clock. It never trusts the phone's wall clock. Clock rollback, boot changes, expired checkpoints, invalid signatures and known revocations fail closed. Existing v1 manifests retain their fingerprint-specific qualification rules.

The native worker discovers upload-confirmed local and relayed reports and checks for updates every 30 seconds while the process is running and connected, as well as existing network/upload triggers. A signed time checkpoint is automatically obtained on first connected launch, before any SOS or responder account is needed, and refreshed at five-minute age. The device-time endpoint verifies installation-key/nonce/boot possession and signs only time; it grants no report or responder privileges. An offline requester must have obtained its own same-boot signed checkpoint while connected; a fresh offline installation or a reboot without connectivity has no trusted time. Relays cannot install authority roots or assert the requester's clock.

Offline proofs retain the deployed 15-minute validity, report binding, revocation epoch, replay history and historical-status semantics. Delivery still needs a Bluetooth contact path; disconnected phones receive no instant updates. A returned RESOLVED status is historical evidence and does not automatically close the SOS. Physical radio/background delivery remains distinct from automated protocol and live HTTP tests.

Migrations 013/014 add a separate custody/device time-proof ledger for installation verifiers rather than placing relay identities in the SOS-origin key registry. First-launch time proof rows have no report reference. All existing origin/custody rows and replay/high-water state are preserved. Each origin/custody proof ledger remains bounded at 10,000 proofs and 64 MiB, with no automatic replay-history deletion.
